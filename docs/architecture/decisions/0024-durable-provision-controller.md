# ADR 0024 — Durable first-provision commands and current permits

Status: adopted for local CL-F25-03/B development, 2026-11-02. Extends ADRs 0020–0023. No production qualifier, installed mutable gateway route or family release.

## Decision

Keep disabled intake immutable. A separate private `DeploymentJobs` domain service creates one first-provision command for an exact allocated intake, with current initiating adult/session/project-node/environment-server authority. Reuse identity execution grants, stored privately in PostgreSQL rather than queues or browser projections. Validate related grants in one bounded identity transaction through `guardExecutions`; the existing single-grant method delegates to it. Require the same current user/session/organization across grants, each original signature/version/expiry and current canonical permission. This avoids nested identity pool leases while preserving existing authorization contracts.

Obtain actual host/world/template/recovery and independent approval qualification through a private port outside identity/runtime transactions. Recheck authority, node/key/project/Minecraft environment, reservation, policy, stop snapshot and fresh hash-bound proof afterward. No production adapter exists; absent qualification is unavailable. A client cannot assert qualification, approval, commands, images, leases or scope. The signed control command binds immutable IDs/plan/template/approval/authorization/policy, first attempt/fence and a lease at most 30s. PostgreSQL persists it, audit and reference-only outbox before delivery. Competing requests cannot create a second command or extend/take over its lease. Automatic retry/lifecycle issuance is not implemented.

Fetch/permit requests require distinct node signatures, exact control/job/node/project/credential/hash binding, current registered certificate fingerprint/lifetime and one-use request IDs. Each fresh nonce-bound permit repeats current original authority and real qualification, is at most 5s and cannot outlive command, session or node credential. Retain at most 64 authenticated fetch/permit records per job; exhaustion denies further effects rather than erasing replay evidence. Shared stop-latch epochs are hashed into the job: an explicit unlatch cannot resume an older command. Local node stop generation/fences remain independent durable safeguards.

Record receipts only after current node/certificate authentication and exact signature/command/tenant/identity/fence binding. Duplicate identical receipts settle once; conflicting receipts are rejected. `succeeded` means the fixed provision command created verified stopped resources, not game readiness. Rolled-back/no-dispatch results retain allocations and storage. Expired/unacknowledged or explicitly uncertain jobs mark the reservation uncertain and retain ports/resources; no blind reissue, takeover, force-release or implicit rollback. Late signed evidence may be attached while keeping an already uncertain job uncertain. Settlement is metadata only, so it never grants a new physical effect after requester revocation.

SQL 0022 supplies forced RLS, composite tenant/node/credential FKs, immutable command/lease/authority references, bounded state transitions and append-only request/outbox records. Queues receive references only. The initial service remains a private port with in-process identity composition in tests; no API/gateway/worker deployment wiring is added. The production gateway must retain its runtime-only DB/key isolation. Do not give API/web/general workers the control key or Docker access, or gateway the identity DB/CSRF secret, to shortcut a remote current-authority adapter.

## Limits and recovery

A daemon effect can complete after lease loss; there is no exactly-once guarantee. First-attempt fence 1 is sufficient only for this one-command-per-intake contract; future lifecycle/retries need a new reviewed durable allocation fence. Current qualifier/approval transport, polling, automatic expiry settlement, physical reconciliation, archival, persistent quota and actual game identity/backup/restore remain gates. Historical records/allocations are retained. Revert application code while preserving the additive schema and history; use forward corrections, never drop a world or erase uncertainty to retry.

Next production composition still needs a remote authorizer/qualified approval/source.
