# ADR 0025 — Separate identity authority from node-control signing

Status: adopted for local CL-F25-03/D development, 2026-11-02. Extends [ADR 0024](0024-durable-provision-controller.md); installed entrypoints remain unchanged and no production qualifier exists.

## Decision

The identity side may validate the two original sealed execution grants but must not hold the node-control signing key or Docker access. The gateway may own runtime state, node-control signing/TLS identity and a separate gateway client certificate, but must not receive identity DB credentials or the identity/CSRF signing secret. Add a private explicitly injected mTLS identity-authority listener and a gateway-side `RemoteDeploymentAuthorizer`; neither is enabled by an installed entrypoint in this checkpoint.

The listener accepts only a strict controller-signed current-grant check, bound to configured controller public key, exact gateway client-certificate fingerprint, organization, fresh nonce, grant digest and a maximum 5s request window. It accepts exactly node:deploy/project and server:provision/environment grants. Validate original signatures/current session/user/membership/canonical permissions together through identity. No grant minting, command execution, arbitrary authorization query, cookie authentication, approval assertion or provider operation is exposed. The listener rejects reusing the node-control private key. Response uses a separate identity-authority Ed25519 key and purpose, exact request/organization/grant/actor/session/version binding and at most 2s freshness. It contains no login/email, sealed grants or credentials. This is current permission evidence, not infrastructure approval or host qualification.

The gateway pins private HTTPS/TLS 1.3 server identity/certificate and authority public key, authenticates with its own certificate and signs with its existing control key. Each check uses a new nonce; no cached proof, retry or fallback is used. Request/response sizes and absolute timeouts are bounded; errors omit values. The optional DeploymentJobs authorizer port returns a narrow principal without profile PII; human admission/read methods remain unavailable if identity is absent. Thus a gateway-only controller can fetch, permit and settle without any in-process identity service.

Keep original session authority expiry separate from proof freshness. Validate freshness before and after each controller SQL callback, rolling back expired-proof writes; cap each node permit to proof freshness as well as job/session/node expiry. A fresh permission proof may become stale when permissions change afterward; the maximum proof window is 2s, and a fresh check is required for every guard. Local stop/fences and current reservation/node/policy/stop-epoch checks still apply. Recheck stop immediately before signing after awaited metadata writes. No proof can revoke a daemon operation already accepted; retain uncertainty after lost authority or acknowledgement.

API-side read-request nonce retention is an in-memory 1,024-entry/5s cache, distinct from PostgreSQL's durable command/effect replay records. Restart does not authorize old effects: clients require a newly generated nonce and valid signed purpose/hash/short time window; original grants are revalidated on every request. Exhaustion/replay denies rather than extending trust. Physical node replay/fences/stop/receipts remain durable in PostgreSQL and the node journal.

## Evidence and remaining work

The real disposable DB/TLS/Redis journey now uses a gateway controller with no injected identity service and a separate remote authority proof listener/key/certificate. Wrong/missing gateway certificate, pin, authority/control key, nonce replay, forged/mismatched/expired requests, cookies and revoked rights deny. Expired-proof controller writes roll back. Test processes share a test runner; this proves protocol composition, not deployed container/process isolation.

Human first-command issuance still uses the local private test issuer. Production admission must persist the original sealed authority through an API-only path and let a separate gateway issuer consume it under fresh remote checks; never deploy the test issuer in API with the control key. Installed configuration/credential lifecycle, polling/expiry/reconciliation/archival, independent approval, real storage/game/backup/restore qualification and explicit production permission remain required. Revert code while retaining schema/immutable grants/jobs/world allocations; no secret-sharing fallback or history deletion.

CL-F25-03/E extension: SQL 0023 and `DeploymentAdmissions` persist the original current adult's sealed dual grants, stop snapshot and at-most-120s metadata authority with immutable scoped bindings/audit/reference-only outbox. Admission accepts no control key or physical operation. Gateway `issueAdmission` consumes that reference under fresh remote current grants/qualification, preserves stop snapshot and caps command expiry to admission. The native fixture now uses this split from its first command. Legacy private in-process `prepare` remains for compatibility/tests with nullable authorization linkage; it must not be exposed in API. No HTTP/worker/entrypoint wiring is added at E.
